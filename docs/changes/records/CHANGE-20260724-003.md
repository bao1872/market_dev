## 需求出处

- 目标：盘后端到端链路从 16:00 调度 → 数据准备 → 统一计算 → 发布 → API → Admin 前端 → 恢复 全流程符合 PRD，修复 4 个实质缺口，删除死代码，不进入部署

## 修改前行为
- 16:00 `worker-bars-scheduler` 直接调 `refresh_all_instruments(trigger_dsa=True)`，DSA 创建逻辑内嵌于行情刷新
- `_maybe_trigger_after_close_orchestrator` 在 DSA completed 后倒序创建 after-close run（已废弃为 no-op 但仍存在）
- `checking_coverage` 只验证日线覆盖率，不验证 15m 覆盖率与最后 bar 时间
- child DSA 跨 worker 恢复：`worker_id` 不匹配直接拒绝，无 re-claim 逻辑
- `publish_run` 已 published 的 run 再次调用抛 `ValueError`，不支持崩溃恢复
- pipeline 展示 8 步（含旧 creating_dsa/waiting_dsa_worker/quality_gate/feature_snapshot）
- 前端硬编码 8 步骤，不动态适配 API 返回
- v4→v5 首次切换方案未明确

## 修改后行为
- 16:00/18:30 调度入口统一调 `create_after_close_run`（幂等），不直接刷新行情或创建 DSA
- orchestrator 内部通过 `claim_for_worker` 创建 DSA，`_owner=after_close_orchestrator` 标记 + `claim_next_run` 排除，generic worker 无法领取
- `refresh_all_instruments(trigger_dsa=False)` 解耦行情刷新与 DSA 创建
- `checking_coverage` 同时验证日线覆盖率 ≥0.9 + 15m per-instrument complete_ratio ≥0.9（按instrument聚合：per_instrument_last_bar = GROUP BY instrument_id MAX(trade_time)；complete_to_close_count = last_bar_time >= 当日14:45 Shanghai 的 instrument 数；complete_ratio = complete_to_close_count / eligible_active_count）；不通过则 `failed`，不创建 DSA
- child DSA 跨 worker 恢复：使用条件原子UPDATE实现 lease epoch fencing（WHERE attempt_count = old_epoch，递增 attempt_count 作为 fencing token，验证 rowcount=1）；旧 worker 使用过期 epoch 写入时 rowcount=0 被拒绝，支持 worker A 崩溃后 worker B 安全接管
- `publish_run` 幂等：已 published 的 run 直接返回，支持崩溃恢复（两阶段幂等发布，故障恢复后达到最终一致）
- pipeline 展示 6 步（refreshing_daily/syncing_boards/checking_coverage/computing_features/publishing/watchlist_ready）；旧四状态映射到 computing_features
- 前端动态读取 API steps + STEP_LABELS 映射，未知步骤降级显示 key
- v4→v5 方案 A：部署新代码后等待首次 v5 盘后运行成功，成功前 watchlist_ready=False，成功后永久切换 v5；不增加 v4 兼容读取代码
- 删除 `_maybe_trigger_after_close_orchestrator` 函数及 `test_worker_auto_trigger.py`
