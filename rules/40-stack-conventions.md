# 技术栈代码约定

## 1. 适用范围

本文件约束仓库当前使用的主要技术栈。

如果项目尚未使用某项技术，不得为了满足本文件而主动引入。

具体版本、目录和入口由 Maps 记录。

---

## 2. Python

### 2.1 类型

- 公共函数、核心业务函数和模块边界必须提供类型标注。
- 避免使用宽泛 `Any` 绕过类型问题。
- 可空值必须显式使用可空类型。
- 返回结构复杂时，优先使用明确模型、TypedDict、dataclass 或 Pydantic Model，而不是无约束字典。
- 不使用类型忽略来掩盖正常可修复的类型错误。

### 2.2 函数

- 一个函数只完成一个清晰动作。
- 参数过多时先检查职责是否混合，不要立即包装成万能配置对象。
- 不使用可变对象作为默认参数。
- 函数名称应体现动作和副作用。
- 核心计算优先保持纯函数。

### 2.3 异常

- 不使用裸 `except`。
- 不使用宽泛 `except Exception` 后静默恢复。
- 自定义异常应表达业务或技术语义。
- 转换异常时保留原始异常链。

### 2.4 异步

- 异步函数中不得执行阻塞 I/O。
- 不因函数标记为 `async` 就默认并发安全。
- 并发数量必须有边界。
- 数据库 Session、HTTP Client 和其他异步资源生命周期必须明确。

### 2.5 Import 与模块

- 禁止通配符 import。
- 避免循环 import。
- 公共类型应放在职责明确的位置。
- 不通过函数内部 import 长期掩盖结构问题。

## 3. FastAPI / API

### 3.1 请求与响应

- 请求参数和响应必须使用明确 Schema。
- API 字段语义必须稳定且可追踪。
- 不直接返回未约束的 ORM 对象。
- 不把内部异常堆栈返回给客户端。
- 业务失败不得伪装成正常成功响应。

### 3.2 路由职责

路由层只负责：

- 输入解析；
- 权限检查；
- 调用应用服务；
- 映射响应。

复杂业务判断、指标计算和数据访问不得直接写在路由中。

### 3.3 兼容性

修改 API 时必须考虑：

- 旧字段；
- 旧客户端；
- 空值语义；
- 默认值；
- 分页和排序；
- 错误结构。

破坏性变化必须由 PRD 明确，并通过兼容路径实施。

---

## 4. SQLAlchemy / 数据库访问

### 4.1 统一入口

- Engine 和 Session 必须通过统一入口创建。
- 业务模块不得自行拼接连接字符串或创建独立 Engine。
- Session 生命周期必须明确。
- 不把 Session 存入全局可变状态。

### 4.2 Repository

Repository 负责数据访问，不负责：

- 页面展示；
- 复杂业务判断；
- 通知；
- 调度；
- 前端格式转换。

Repository 方法名称应表达查询或写入范围。

### 4.3 查询

- 避免 N+1。
- 明确加载策略。
- 批量读取优先于循环查询。
- 只选择实际需要的字段。
- 大数据查询必须有范围和分页或流式策略。

### 4.4 写入

- `UPDATE` 和 `DELETE` 必须有明确过滤条件。
- 批量写入应说明幂等和冲突策略。
- 事务中避免不必要的网络调用。
- Commit、flush 和 rollback 的责任必须明确。

### 4.5 Migration

- 已执行的历史 Migration 不直接修改。
- Schema 变化和大规模数据回填应分开。
- Migration 应可审查且影响范围明确。
- 不在 Migration 中执行不可控的长时间业务任务。

---

## 5. TypeScript

### 5.1 类型

- 禁止无理由使用 `any`。
- API 类型应集中定义或由统一 Schema 生成。
- 对未知外部数据使用 `unknown` 并在边界校验。
- 可空、可选和未加载状态必须区分。
- 不通过类型断言掩盖真实类型不一致。

### 5.2 函数与对象

- 函数输入输出明确。
- 避免修改传入对象。
- 不把多个不相关状态塞入一个大型对象。
- 枚举或联合类型优于散落字符串。

---

## 6. React

### 6.1 状态归属

- 状态放在最低但足够共享的拥有者中。
- 跨页面或跨模块状态由明确 Store 或 URL 管理。
- 同一状态不得同时由 URL、本地 State 和全局 Store 独立拥有。

### 6.2 派生值

- 可从 props 或 state 计算出的值不重复存储。
- `useEffect` 不用于普通派生计算。
- 缓存计算只在存在真实性能需要时使用。

### 6.3 Effect

Effect 只用于与外部系统同步，例如：

- 网络；
- 订阅；
- DOM；
- 定时器；
- 外部 Store。

Effect 必须：

- 依赖完整；
- 清理资源；
- 避免重复请求；
- 处理组件卸载；
- 避免竞态覆盖。

### 6.4 组件

- 展示组件不承载复杂业务逻辑。
- 不在多个组件复制业务判断。
- 组件 Props 应最小且语义明确。
- 列表 key 必须稳定，不能依赖易变化的索引。
- 加载、空值、错误和权限状态必须明确。

### 6.5 请求状态

请求必须明确处理：

- loading；
- success；
- empty；
- error；
- stale；
- cancelled。

不得用空数组同时表示未加载、无数据和失败。

---

## 7. 配置

- 所有环境相关参数通过统一配置层读取。
- 业务代码不得直接读取散落环境变量。
- 配置缺失应明确失败或使用经过确认的安全默认值。
- 密钥不得写入仓库。
- 配置名称应与语义一致，避免同一概念多个名称。

---

## 8. 格式与自动检查

- 使用项目已有格式化、Lint 和类型检查工具。
- 不为局部修改更换整套工具链。
- 不通过关闭规则、全局 ignore 或大范围格式化掩盖真实问题。
- 自动格式化产生的大范围无关变化应避免进入局部提交。
