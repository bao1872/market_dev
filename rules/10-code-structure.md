# 代码结构规则

## 1. 单一职责

函数、类和模块应具有明确职责。

一个单元不应同时承担多个无关角色，例如：

- 解析输入；
- 查询数据库；
- 计算业务结果；
- 修改状态；
- 发送通知；
- 拼装页面展示。

职责是否过多的判断标准：

- 修改一个原因时是否经常影响无关代码；
- 单元名称是否无法准确概括其职责；
- 单元是否需要大量模式开关；
- 单元是否被不同调用方以完全不同方式使用。

## 2. 分层边界

不同层只承担自己的职责。具体目录以项目 Maps 为准，但逻辑边界必须明确。

典型职责：

| 层 | 主要职责 |
|---|---|
| API / Controller | 输入解析、权限、调用编排、响应映射 |
| Service / Application | 用例编排、事务协调、业务流程 |
| Domain / Compute | 核心业务规则和纯计算 |
| Repository / Data Access | 数据读取和持久化 |
| Worker / Job | 任务包装、调度输入、执行状态 |
| Frontend View | 展示和交互 |
| Frontend State / Data | 请求、缓存、页面状态 |

禁止：

- API 层直接承载复杂业务算法；
- Repository 决定业务结果；
- Worker 复制核心领域逻辑；
- 前端重新实现后端权威业务判断；
- 展示组件直接修改跨页面共享状态。

## 3. 依赖方向

依赖应从外层指向内层能力，而不是让核心逻辑依赖具体运行环境。

核心计算不应直接依赖：

- Web 请求对象；
- UI 组件；
- Redis 客户端；
- 数据库 Session；
- 全局环境变量；
- 具体任务框架。

需要外部能力时，通过明确参数、接口或外层编排提供。

## 4. 纯逻辑与副作用分离

能够写成纯函数的核心逻辑，应尽量保持：

```text
输入 + 参数 → 输出
```

以下副作用应位于明确边界：

- 数据库写入；
- Redis 操作；
- 文件读写；
- 网络请求；
- 日志；
- 通知；
- 时间读取；
- 随机数。

不得把计算、持久化和通知揉成无法独立验证的单一函数。

## 5. 公共入口唯一

同类基础能力应通过统一入口使用，例如：

- 配置；
- 数据库连接；
- Session；
- Redis Client；
- API Client；
- 序列化；
- 时间转换；
- 公共业务计算。

业务模块不得绕过统一入口自行创建另一套实现。

## 6. 避免循环依赖

模块之间不得形成循环导入或双向职责依赖。

发现循环依赖时，应优先检查：

- 职责是否混合；
- 公共类型是否放错位置；
- 上下层边界是否倒置；
- 是否存在隐式共享状态。

不得通过运行时导入、字符串导入或复制代码长期掩盖循环依赖。

## 7. 避免万能模块

禁止长期存在职责不清的：

- `utils` 大杂烩；
- `helpers` 大杂烩；
- 万能 Service；
- 万能 Manager；
- 同时管理多个领域的 Store；
- 无边界的公共常量文件。

公共代码应按明确语义和责任组织。

## 8. 接口最小化

函数、类和模块只暴露调用方真正需要的能力。

避免：

- 暴露内部可变状态；
- 返回包含大量无关字段的对象；
- 让调用方依赖内部 ORM 细节；
- 使用一个万能方法承载多个不同动作；
- 通过布尔参数切换完全不同的行为。

## 9. 组合优于继承

没有稳定“是一个”关系时，优先通过组合复用能力。

不得为了复用少量代码建立复杂继承树。

继承层级应保持浅，并且子类不得改变父类契约。

## 10. 结构变化同步 Maps

当以下关系发生变化时，应更新对应 Map：

- 主要入口；
- 模块职责；
- 依赖方向；
- 数据流；
- 任务链路；
- API 与前端关系；
- 权威实现位置。

普通函数内部修复不需要更新 Maps。
