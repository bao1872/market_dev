## 1. 摘要

盘后 `refreshing_daily` 长任务（全市场日线刷新，耗时随 instrument count / backfill window / provider throughput 变化）此前被固定 `STEP_TIMEOUT=3600s` 的 absolute wall-clock 上限误判为 `STEP_TIMEOUT` 失败，而实际数据已完整、仅耗时超过固定秒数（回补 4 天约 42min > 3600s）。本轮将 long-running business step 的失败判定从「total_elapsed > fixed generic duration」改为「仅显式 execution failure / 正式治理认定的 no-progress / 权威 PRD 明确的 business deadline」，并补全治理四类超时隔离。

## 2. 背景与问题

- 变化前：`after_close_orchestrator._STEP_TIMEOUT_SECONDS["refreshing_daily"] = 3600`，由 `asyncio.wait_for(operation(), timeout=3600)` 强制；只要总耗时 > 3600s 即 `STEP_TIMEOUT`，不区分「持续 progress 的长任务」与「真卡死」。
- 触发事实：2026-08-07 after-close run（run_id `3c35387e-...`）在 `refreshing_daily` 步 STEP_TIMEOUT，但 `bars_daily` 08-07 已 5286 行完整 → 数据非缺失，根因是摄入步耗时随回补窗口变化，非 board 逻辑问题。
- 治理缺口（GOVERNANCE_GAP）：既有 `rules/80` §13 长任务仅讲资源纪律，未区分 ①基础设施命令超时 ②长任务业务绝对超时 ③卡死/无进展 ④业务截止时间；PRD 也无对应 liveness 契约。
- §22 false-liveness 风险：原 `_tick_loop` 把 heartbeat 时间当成 `last_progress_at`，在 CPU-bound / blocking provider call 期间仍会刷新，不能证明业务有进展。

## 3. 变化前

- `_STEP_TIMEOUT_SECONDS["refreshing_daily"] = 3600`；注释误称「约 13 分钟」。
- `_tick_loop` 每 10s 刷新 `summary["last_progress_at"] = now`，heartbeat 冒充业务 progress。
- `_run_with_cancellation` 内部 `deadline = loop.time() + timeout_seconds`，不支持 `None`。
- 治理无四类超时隔离；`DS-107`（`app/utils/long_task_budget.py`）只管资源/checkpoint/resume，不含 liveness 政策。

## 4. 变化内容

- PRD 31 新增 **PC-43 Long-running step liveness contract**（不写实现数字：3600/5400/7200/heartbeat interval/stall seconds 属 Rules/Config/Runbook/Code）。
- PRD 30 §AC-16 补最小引用：long-running liveness 以 PC-43 为准。
- Rules 80 §13.1 扩展四类超时隔离（A 基础设施命令 / B 长任务业务绝对超时禁止 generic fixed / C stall=now-last_real_progress / D business deadline）；§13.2 progress-heartbeat 正确性；§13.3 resume/data safety 不变；§13.4 边界（不取消基础设施命令超时）。
- Code（`after_close_orchestrator.py`）：
  - `refreshing_daily` 的 `_STEP_TIMEOUT_SECONDS` 设为 `None`；`_step_timeout` 返回类型放宽为 `float | None`。
  - 移除 `_tick_loop` 把 heartbeat 时间冒充 `last_progress_at` 的逻辑（修复 false-liveness）。
  - `_run_with_cancellation` 支持 `timeout_seconds=None`：不设 absolute deadline，仅保留协作取消（cancellation_check）。
  - 防御 `error_message` 在 `None` 时不崩。
- Runbook `after-close-remote-development-run.md`：新增 §3.4 RUNNING LONG ≠ STALLED 判断准则；安全边界补「长任务仍有 progress 时禁止 cancel/retrigger，仅 stall 才走正式 recovery/resume，禁止直接 SQL 改状态/写 pointer」。

## 5. 变化后

- `refreshing_daily` 无 absolute timeout，只要持续 valid progress 即允许自然完成（40min/80min/2h 均正常），由 stale watchdog（lease 过期 + heartbeat 不健康）防护无进展卡死。
- 治理明确四类超时隔离，long-running business step 不再被 generic fixed absolute timeout 误判。
- heartbeat 不再冒充业务 progress，last_progress_at 仅在业务推进或 finally 时更新。
