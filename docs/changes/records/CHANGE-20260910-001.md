## Why

2026-08-27 两份根目录 checkpoint 记录了当时发现的 Snapshot Ownership 问题：

- `PHASE_B1_REPORT.md`：base 唯一键不含 run 身份，直接 rerun 会产生 A/B mixed-world 风险（SCHEMA_BLOCKER → STOP）。
- `PHASE_B1_1_DESIGN.md`：提出 dual partial-index（CURRENT universe `base + source_run_id NOT NULL` / LEGACY universe `base + source_run_id IS NULL`）+ `DISPLAY_CORE_OWNER` 设计，并指 `FactorPublication(kind=stock_core).data_run_id` 已成为 stale display pointer。

后续实现**未采用 dual-index migration**，而是分别落地：

1. **application-level published-run 保护**：`create_snapshot_run` 的 `PublishedSnapshotRunExistsError` + `upsert_snapshot` WHERE（仅保护 succeeded+published run）；
2. **Review-lineage 显示归属**：`current_core_run_service.resolve_current_core_run`（formal Review → `source_core_run_id` → `StockFeatureSnapshotRun`），取代 `FactorPublication(stock_core)` 为 CURRENT authority（commit `ef5c3a76` / `a71516e4`，2026-09-02）。

这两套机制解决了：published canonical 保护、display authority。
**未解决**：schema-level A/B coexistence（D1）、backfill NULL lineage（D2）。

继续把两份 PHASE 文档留在仓库根目录会与正式 `docs/` 体系平级，制造假权威。故将当前事实并入 Map、历史推理并入本 Change、删除两份根目录文档。
