# 测试代码规则

## 1. 测试面向行为

测试应验证：

- 对外行为；
- 输入输出；
- 边界条件；
- 错误处理；
- 重要状态变化；
- 数据写入结果。

避免过度绑定：

- 私有函数；
- 内部调用顺序；
- 无业务意义的实现细节；
- 临时目录结构。

正常重构不应导致大量无意义测试重写。

## 2. 一个测试表达一个主要意图

测试名称应说明：

- 在什么条件下；
- 执行什么行为；
- 预期什么结果。

一个测试可以包含完成同一行为所需的多个断言，但不应同时验证多个无关能力。

## 3. 测试独立

测试不得依赖：

- 执行顺序；
- 其他测试留下的数据；
- 本地机器历史状态；
- 当前时间偶然值；
- 不受控外部服务；
- 全局缓存残留。

每个测试应自行建立并清理必要状态。

## 4. 测试数据最小且可读

测试数据应：

- 只包含验证行为所需字段；
- 清楚表达场景；
- 使用确定值；
- 避免无意义大型 Fixture；
- 避免复制生产全量数据。

复杂领域案例可以使用命名 Fixture，但来源和用途必须清楚。

## 5. Mock 只隔离边界

Mock 适合隔离：

- 外部网络；
- 第三方服务；
- 时间；
- 随机数；
- 不稳定基础设施。

不得把被测试的核心业务逻辑本身 Mock 掉。

过度 Mock 导致测试只能证明调用发生，而不能证明行为正确。

## 6. 回归测试

重要 Bug 修复在适合时应增加能复现原问题的测试。

回归测试应：

- 在修复前失败；
- 在修复后通过；
- 直接覆盖根因；
- 避免只验证表面症状。

普通样式或低价值一次性问题不强制增加自动化测试。

## 7. 边界和失败场景

核心逻辑测试不应只覆盖正常路径。

根据风险考虑：

- 空输入；
- 缺失字段；
- 极值；
- 重复调用；
- 部分失败；
- 超时；
- 并发；
- 旧数据；
- 非法状态转换。

## 8. 时间和随机性可控

测试不得直接依赖真实当前时间或不可控随机结果。

应使用：

- 固定时间；
- 注入时钟；
- 固定随机种子；
- 明确输入。

## 9. 数据库测试

数据库测试应明确：

- 使用的数据库范围；
- 事务或清理策略；
- 唯一约束；
- 重复执行；
- 提交与回滚；
- 并发冲突。

不得依赖测试执行后人工清理。

## 10. API 测试

API 测试至少关注：

- 状态码；
- 响应 Schema；
- 字段语义；
- 权限；
- 错误结构；
- 空值和分页边界。

不应只断言请求返回 200。

## 11. 前端测试

前端测试优先验证用户可观察行为：

- 页面状态；
- 交互；
- 跳转；
- 筛选和排序；
- 加载、空值和错误；
- 权限；
- 请求结果展示。

避免只测试内部 state 或实现细节。

## 12. 测试代码同样遵守生产代码规则

测试代码不得：

- 大量复制；
- 隐式共享状态；
- 吞异常；
- 使用不稳定等待；
- 用超长 sleep 解决竞态；
- 用宽泛断言掩盖结果差异。

## 13. 不修改测试来迎合错误实现

当测试与代码冲突时，先判断：

- PRD 是否变化；
- 测试是否过期；
- 代码是否存在 Bug。

不得仅为了让 CI 通过而降低断言、删除失败测试或修改预期结果。
