# Changes

## 1. 定位

`docs/changes/` 保存盘迹的重要演化历史，回答：

> 为什么系统从原来的状态变成现在的状态，实际改变了什么，如何迁移，又通过什么证据确认。

Change 不是开发日报、提交清单或普通 Bug 记录。

## 2. 与其他文档的边界

| 文档 | 职责 |
|---|---|
| PRD | 定义目标状态 |
| Maps | 记录当前实现 |
| Changes | 保存重要转变的原因、范围、迁移和验证 |
| Runbooks | 记录可重复操作步骤 |
| Git 历史 | 记录普通代码修改和小 Bug |

Change 不复制完整 PRD，也不长期保存当前代码入口。当前实现始终以 Maps 为准。

## 3. 创建门槛

符合以下任一条件时创建 Change：

1. 改变已确认的产品或业务行为；
2. 改变 API、Schema、字段、状态或数据语义；
3. 改变主要模块责任、调用链或权威入口；
4. 改变运行环境、调度、发布或部署方式；
5. 涉及重要数据迁移、修复、回填或全量重算；
6. 修复造成数据、权限、发布或稳定性风险的重大故障；
7. 未来开发者必须知道为什么系统会采用当前设计。

以下通常不创建 Change：

- 普通小 Bug；
- 文案和样式；
- 局部内部重构；
- 测试补充；
- 普通依赖升级；
- 单次部署或补跑；
- 不改变责任和契约的性能优化。

## 4. ID 与命名

格式：

```text
CHANGE-YYYYMMDD-NNN-short-slug.md
```

例如：

```text
CHANGE-20260726-001-documentation-governance.md
```

规则：

- 日期使用 Change 建立日期；
- `NNN` 为当天顺序；
- ID 创建后不得修改；
- 文件按年份存放；
- slug 使用简短英文，不承担事实语义。

## 5. 类型

| 类型 | 使用场景 |
|---|---|
| `behavior` | 产品或业务行为变化 |
| `contract` | API、Schema、字段或状态语义变化 |
| `architecture` | 模块、职责、调用链或权威入口变化 |
| `runtime` | 环境、服务、调度、发布或部署变化 |
| `data` | 数据迁移、修复、回填或重算 |
| `incident` | 重大故障和系统性修复 |

一份 Change 只指定一个主类型，可以增加领域标签。

## 6. 状态

- `进行中`
- `已完成`
- `已回滚`
- `被后续变化替代`

标记“已完成”必须满足：

1. 变化已经实施；
2. 必要验证已经完成；
3. 对应 Maps 已更新；
4. 需要修改的 PRD 已更新；
5. 迁移和遗留风险已明确。

## 7. 创建流程

### 需求或行为变化

```text
更新 PRD
→ 开发与迁移
→ 验证
→ 更新 Map
→ 完成 Change
```

### 不改变需求的架构变化

```text
PRD 不变
→ 修改实现
→ 验证行为不变
→ 更新 Map
→ 完成 Change
```

### 重大故障

```text
恢复关键能力
→ 确认根因和影响
→ 实施系统性修复
→ 验证
→ 更新 Map/Runbook
→ 完成 Change
```

## 8. 历史不可变

Change 标记“已完成”后原则上不重写历史。

允许：

- 修正错别字；
- 补充链接；
- 增加后续 Change 引用；
- 标记已回滚或被替代。

不允许：

- 删除失败记录；
- 把未验证改写为已验证；
- 用当前实现覆盖当时状态；
- 为了让历史更整齐而修改原始原因。

后续发生新变化时创建新的 Change。

## 9. 回滚

回滚时：

1. 保留原 Change；
2. 新建回滚 Change；
3. 原 Change 标记为“已回滚”或“被后续变化替代”；
4. 更新 Maps 为回滚后的真实状态；
5. 只有目标要求改变时才修改 PRD。

## 10. 文件

| 文件 | 职责 |
|---|---|
| `INDEX.md` | 全局索引 |
| `TEMPLATE.md` | 标准模板 |
| `YYYY/CHANGE-...md` | 具体重要变化 |
