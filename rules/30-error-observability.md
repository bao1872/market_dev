# 错误处理与可观察性规则

## 1. 不吞异常

禁止无处理地捕获异常，例如：

```python
try:
    ...
except Exception:
    pass
```

捕获异常后必须明确选择：

- 处理并恢复；
- 转换为更准确的错误；
- 记录必要上下文后继续抛出；
- 标记降级结果；
- 记录失败状态。

## 2. 失败不能伪装成成功

不得通过以下方式把失败表现为正常结果：

- 返回空对象；
- 返回零值；
- 返回默认状态；
- 返回 HTTP 200；
- 标记任务完成；
- 忽略部分失败；
- 静默使用旧缓存。

缺失、失败、无结果和正常空结果必须区分。

## 3. 错误必须分类

错误至少应在逻辑上区分：

- 输入无效；
- 业务条件不满足；
- 数据缺失；
- 外部依赖失败；
- 超时；
- 并发冲突；
- 系统内部错误。

调用方必须能够据此决定：

- 是否重试；
- 是否提示用户；
- 是否降级；
- 是否终止任务；
- 是否记录失败状态。

## 4. Fallback 必须显式

使用备用路径时，应能识别：

- 原路径失败原因；
- 实际使用的备用路径；
- 是否产生降级结果；
- 是否需要后续修复。

不得用 fallback 长期掩盖主路径故障。

## 5. 错误信息包含上下文

错误和关键日志应包含足够定位问题的上下文，例如：

- 对象标识；
- 请求或任务标识；
- 处理阶段；
- 输入范围；
- 外部依赖；
- 重试次数。

不得只记录“失败”“异常”或完整堆栈而没有业务上下文。

## 6. 不泄露敏感信息

日志、异常和 API 响应中不得输出：

- 密码；
- Token；
- 私钥；
- 完整连接字符串；
- 认证 Header；
- 用户敏感数据。

内部日志可以保留必要技术上下文，但必须脱敏。

## 7. 日志级别应有意义

建议语义：

- `DEBUG`：开发诊断细节；
- `INFO`：正常关键阶段和结果摘要；
- `WARNING`：发生可恢复异常、降级或潜在风险；
- `ERROR`：当前操作失败，需要处理；
- `CRITICAL`：系统关键能力不可用或存在严重数据风险。

不得把正常高频事件全部记录为 WARNING 或 ERROR。

## 8. 日志不能替代结构化状态

需要被程序查询、判断或恢复的状态，必须存储为结构化数据。

例如任务状态、处理阶段和发布状态不能只存在于日志文本中。

## 9. 高频路径控制日志量

循环、批量计算和高频请求中不得无边界输出日志。

应使用：

- 汇总日志；
- 分阶段日志；
- 限频；
- 抽样；
- 失败明细加汇总。

但不能因为控制日志量而失去关键失败信息。

## 10. 重试必须有边界

重试应明确：

- 最大次数；
- 间隔或退避；
- 可重试错误类型；
- 幂等条件；
- 最终失败状态。

禁止无限重试和无差别重试。

## 11. 部分成功必须明确

批量任务出现部分失败时，必须清楚表达：

- 总数；
- 成功数；
- 失败数；
- 跳过数；
- 失败对象；
- 是否允许发布或继续。

不得只因为部分成功就标记整个任务成功。

## 12. 可观察性服务于定位和恢复

日志、指标和状态的目标是帮助回答：

- 问题发生在哪里；
- 影响了什么；
- 是否仍在继续；
- 是否可以重试；
- 是否已经恢复。

不得为了“日志完整”记录大量无行动价值的信息。
