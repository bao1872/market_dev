# 50 Git 与开发流程

> 来源：AGENTS.md 第 8 节与 Git 工作协议

## 分支模型（dev-only）

仓库只保留三个长期分支，未经用户明确授权禁止创建任何新分支：

| 分支 | 职责 | 约束 |
|---|---|---|
| `dev` | 唯一默认日常开发分支 | 所有变更默认直接在 `dev` 提交；`dev` 是手工 CI 与手工部署的唯一来源；push 本身不触发 workflow 或部署 |
| `main` | 阶段性稳定锚点 | 未经明确授权不得修改、合并或推送 |
| `experiments` | 明确授权下的隔离实验 | 不得作为远程开发部署来源；进入 `dev` 前必须明确审查 |

硬约束：

- 未经用户明确授权，禁止创建任何新的本地或远程分支，**包括 backup 分支**；
- 未经用户明确授权，禁止切换工作分支（`git checkout` / `git switch` 到 `dev` 以外的分支）；
- 未经用户明确授权，禁止对任何分支 force push；
- 需要可恢复点时，使用 **checkpoint commit** 而不是新建分支；
- 无法以 fast-forward 方式对齐时必须停止并报告，不得自行 merge、rebase 或覆盖。

## 提交说明要求

每个提交（或一组紧密相关提交的说明）必须能回答：

- 当前系统原来如何运行；
- 本次为什么修改；
- 修改了哪些代码 / docs/maps（`docs/current` 已标记 legacy 只读，不再要求同步）；
- 新增哪个 CHANGE；
- 是否改变 API / 数据模型 / Worker 或第三方集成；
- 测试结果；
- 是否仍有 Known Gap；
- 是否需要生产验证。

## 提交安全

禁止 `git add -A` / `git add .` / `git add -u`；必须精确 `git add <file>`。

不得提交：

- `.vscode/settings.json`；
- `.traeignore`；
- `node_modules/`；
- `.venv/`；
- `__pycache__/`；
- `*.py[cod]`；
- `.mypy_cache/`；
- `.pytest_cache/`；
- `.ruff_cache/`；
- `.coverage`；
- `coverage.xml`；
- `dist/`；
- `build/`；
- `*.log`；
- `*.csv`；
- `*.parquet`。

## 删除保护

未经用户明确授权禁止删除：

- 数据库卷；
- 运行中容器；
- postgres / redis 数据目录；
- node_modules；
- .venv；
- .git；
- 源码；
- 共享开发业务数据。

## GF-100 任务产物收尾

> 本条是任务结束时应如何盘点并清理本轮产生的临时产物的合同。
> 目标：既不把调试/测试/构建的临时产物残留成脏目录，也绝不错删持久或有价值的数据。

### 可自动删除的前提条件

满足以下**全部**条件才允许任务收尾时自动删除一个临时产物：

1. 本轮任务**确实创建**了该产物（有创建证据，不是历史遗留）；
2. 用途已结束，且不会在后续步骤中被复用；
3. 仓库中无活跃代码 / 测试 / 工具引用它；
4. 用户已明确授权删除（或该产物属于下文「应清理清单」且不属于「不得自动删除清单」）。

### 应清理清单（满足前提条件时可清理）

- 临时脚本（一次性分析 / 探查用的 `python -c` 落地文件、`/tmp/*.py`、非正式脚本）；
- 一次性调试日志与临时输出（非 `docs/`、非正式日志目录的临时 log）；
- 临时 JSON / CSV / 中间数据导出（非正式 fixture、非业务导出）；
- 调试截图 / 临时图片（非正式 baseline、非 UI 验收必须留存的证据图）；
- 构建残留与各类缓存目录（`__pycache__/`、`.pytest_cache/`、`.mypy_cache/`、`.ruff_cache/`、临时 build 产物等）；
- 本轮临时创建后已确认不再需要的文件（由创建记录可追溯）。

### 不得自动删除清单（即使满足部分条件也不得自动删）

- `.venv` / `node_modules` / 正式依赖目录；
- 正式测试 fixtures（如 `backend/tests/fixtures/**`，含 SMC parity、Playwright baseline）；
- 用户上传的输入文件、业务导出、历史数据；
- 来源不明或未知所有者文件；
- 任何数据库、Docker volume 或其中的数据；
- 未获授权删除的历史文件（见上文「删除保护」）。

### 最终报告必填四字段

任务收尾报告必须输出以下四个字段，不得省略：

1. **创建清单**：本轮创建了哪些临时产物（路径）；
2. **删除清单**：实际删除了哪些（路径 + 删除依据）；
3. **保留清单**：保留了哪些本可清理的（路径）；
4. **保留原因**：每条保留项的保留理由（引用上文「不得自动删除清单」对应条款）。

> 治理检查 `tools/check_governance_rules.py` 不直接扫描任务报告；
> 本条以运行约定落地。涉及部署的产物清理见 `80-deployment-data-safety.md` DS-105。

## 分支保护

- 未经明确授权修改、合并或推送 `main`：禁止；
- 未经明确授权创建任何新分支（含 backup 分支）：禁止；
- 未经明确授权切换到 `dev` 以外的工作分支：禁止；
- 对任何分支 force push：未经明确授权禁止；
- 以 `experiments` 作为远程开发部署来源：禁止；
- 为通过检查削弱 `check_docs_consistency.py`：禁止。

## 执行模式

### 继续执行模式

当任务 checkpoint 匹配时，不重复审计和规划，直接从断点继续。

断线恢复校验仅检查：

- 当前分支必须是 `dev`，并核对 HEAD；
- 未提交文件；
- 冲突标记；
- 编译；
- diff check。

通过后立即继续当前任务。禁止在继续模式下重新规划已完成步骤或全仓审计。

### 前台串行执行

默认前台串行执行测试和检查命令。

- 禁止强制 `nohup` 后台测试；
- 仅当单条命令预计超过 5 分钟且用户明确同意时才可使用后台日志方式；
- 测试组之间必须串行，禁止并行构建或并行测试。

## 通用执行主体合同（2026-08-02 收口）

**项目治理不按 IDE、Agent、模型或客户端区分角色。**

- 所有 IDE、编码助手和自动化 Agent 遵守同一套仓库规则；
- 治理按**实际操作**定义（是否改代码、是否连生产、是否执行部署、是否写数据），
  不按工具名称区分；
- 规则文件中**不得**出现按工具命名的角色定义、能力矩阵、模式切换表或专属状态值；
- 一个执行主体能做什么，取决于用户在本轮授予的授权和本文件 §基础安全边界，
  而不取决于它是哪个工具。

### 提交与推送（所有执行主体一致）

- 开始任务时必须 `git fetch origin dev`；
- 必须确认当前分支为 `dev`，且 `git merge-base --is-ancestor origin/dev HEAD` 退出码为 0；
- 只有祖先检查通过才允许继续；若 `origin/dev` 已前进、不是当前 HEAD 祖先，
  必须停止并报告，不得自行 merge、rebase 或覆盖；
- 完成后使用 `git push origin dev` 以 fast-forward 方式推送；
- 只允许 fast-forward，**禁止 force push**；
- 未经明确授权禁止创建新分支（含 backup 分支）、禁止切换工作分支；
- 需要可恢复点时使用 checkpoint commit；
- 禁止 `git add -A` / `git add .` / `git add -u`，必须精确 `git add <file>`。

### 部署来源

- `dev` 是手工 CI 与开发部署的唯一来源；
- push `dev` 不触发自动部署，CI 也不是部署前置条件（见 `40-testing-quality.md` TQ-90）；
- `main` 是阶段性稳定锚点，未经明确授权不得修改、合并或推送。

### 高风险操作按操作本身授权

以下操作不因执行主体是哪个工具而自动获得或丧失权限，一律需要用户在本轮明确授权：

- 执行部署脚本、修改 Compose / 部署脚本 / 服务器配置；
- 连接共享开发业务数据库、生产飞书账户，或对生产做任何写操作；
- 执行 migration；
- 删除数据库卷、运行中容器、源码或共享开发业务数据；
- force push 或创建/切换分支。

未获授权时，只能进行只读核验并如实报告，不得自行降级为"临时方案"绕过。
